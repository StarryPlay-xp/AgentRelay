# Codex 会话“立即引导 / 排队发送”调研与测试

> 2026-11-17。三个阶段都已完成：只读调查、隔离测试、桌面端专用测试会话（第 6.2 节）。改造方案（第 7 节）已实现，单元测试、集成测试通过（第 7.8 节），并用开发版在桌面端专用测试会话上做完了端到端验收（第 9 节）。
> 本文按 README 的隐私约定书写：路径写成 `~/…`，不出现真实会话编号。

## 1. 结论

| 问题 | 结论 | 依据 |
|---|---|---|
| 能否对桌面端现有会话**排队发送**（Queue） | **能，而且现在就是这么做的。** AgentRelay 用的 `codex queue` 底层是 Codex 自带的持久化队列：对方忙时不打断，正常结束后立即新开一轮处理；用户按停止后不会马上自动执行 | 源码 + 隔离实测 T2、T4、T10、T13；**桌面端当前版本实测 A、B 段通过** |
| 用户按停止后，排着的信会一直停着吗 | **不会。** 只停到“下一次有任何一轮正常结束”为止：点“会话的继续”续跑完被中断的任务，或者用户自己再发一条消息并回复完，排着的信都会自动接着执行 | 桌面端 B 段 + 隔离实测 T10b + 源码 |
| 能否用 App Server 的 `turn/steer` 对桌面端现有活跃会话**立即引导**（Steer） | **当前版本不能。** 协议本身可用，但外部程序连不到桌面端那个服务进程，另起实例又被 Codex 的写入锁挡住 | 第 4 节逐条核查；隔离实测 T1～T12 |
| 有没有不靠内部接口的替代路线 | **有，而且桌面端实测成立：Codex 官方钩子**（`PreToolUse` + `PostToolUse` + `Stop`）。信到之后，对方要执行的下一条命令会先被拦下、信随之送到；正在跑的命令结束时、或本轮即将结束时也会送到；都在**同一轮次**里，对方空闲时不会凭空开新轮次 | 官方文档 + 隔离实测 H0～H4、P1、P2 + **桌面端实测 C、D、E 段和空闲测试通过** |

一句话：**排队现在就可靠，但“停止”挡不住它太久；立即引导走 `turn/steer` 走不通，走官方钩子在你的桌面端现有会话上已经实测成立——信到之后，对方不会再开始任何新命令就会先收到信。**

按任务书的成功标准（发送方显式选择 → 接收方按该模式处理 → 有可核对回执）：

| 模式 | 显式选择 | 接收方按模式处理 | 可核对回执 | 现状 |
|---|---|---|---|---|
| queue | 已实现（`delivery="queue"`，默认） | **桌面端当前版本已实测**，经 AgentRelay 开发版端到端验收 | 有排队编号；超时改为“结果未知”并核对；“已处理”目前只能靠回信判断 | **达成**（第 9 节 V1） |
| steer（turn/steer） | — | 桌面端做不到 | — | **不可行** |
| steer（钩子） | 已实现（`delivery="steer"`、`steer_fallback`） | **经 AgentRelay 开发版在桌面端端到端验收**：三条入口都送进同一轮，对方读到正文 | 回执记录要求的模式、实际模式、注入的轮次和钩子事件；对方读信后为“对方已读” | **达成**（第 9 节 V2～V6）；对方是否照信做取决于对方模型和你的授权 |

## 3. 现在的投递链路（AgentRelay → Codex）

```
relay_send（RelayMCP.swift:124）
  → relay-mcp 经本机通话口转给中转核心
  → RelayService.send（RelayService.swift:265；给 Codex 的分支在 :343）
  → CodexDispatcher.deliver（Delivery.swift:112，同一收件会话串行，失败按 5/15/45 秒重试）
  → CodexCLI.enqueue（Delivery.swift:47）执行：codex queue --thread <会话编号> --message <信封+正文>
      codex queue 在自己进程里起一个“内嵌 App Server”，调用实验性方法 thread/queue/add
      （codex 源码 tui/src/session_queue_commands.rs）
  → 信写进 ~/.codex 下的 SQLite 持久化队列
  → 桌面端的 App Server（ChatGPT 拉起的那个）里的队列扩展：
      · 每 10 秒看一次数据库有没有变化（ext/queue/src/service.rs:90-246）
      · 会话空闲、且上一轮不是被中断的，就取一条用 start_turn_if_idle 开新轮次（:440-509）
      · 每当一轮“正常结束”，立刻再派发下一条；被中断则不派发（:588-605）
```

要点：

- 这就是“排队发送”，没有“立即引导”的入口。`relay_send` 和 `send_message_to_thread`（桌面端内置工具，由 ChatGPT 自己处理）都没有发送模式参数。
- 对方空闲时要等下一次 10 秒检查，所以设计方案里实测是“约 7～20 秒后开始”；对方正忙时，本轮一结束就接着执行（T13 实测 0 秒）。
- 三个现有隐患（第 7.6 节处理）：
  1. Codex **不按消息编号去重**（T7：同一个 `clientUserMessageId` 排两次就执行两次）。而 `CodexCLI` 超时（30 秒）时信可能已经排进去了，`CodexDispatcher` 仍会重试，可能重复投递。
  2. 状态只有“已排队”，看不出对方是否已经开始处理。
  3. README 和设计方案第 11.1 节第 7 点说“手动停止后队列暂停，要到会话里点继续”。实测不完整：桌面端有**两个**“继续”按钮（会话的、排队消息的），而且不点任何按钮、自己再发一条消息并回复完，排着的信也会自动执行（第 6.2 节 B 段、T10b）。

## 4. 外部程序能不能连到桌面端正在用的会话

| # | 核查项 | 结果 | 依据 | 是实测还是推断 |
|---|---|---|---|---|
| 1 | 桌面端 App Server 怎么启动 | ChatGPT 主进程用标准输入输出管道拉起（参数里没有 `--listen`），只服务 ChatGPT 自己 | `ps` 看参数；`lsof` 看到它的输入输出是和主进程相连的一对套接字，**没有任何监听中的套接字** | 实测（只读） |
| 2 | 公开的共享服务（daemon）控制套接字 `~/.codex/app-server-control/app-server-control.sock` | 不存在；`codex app-server daemon version` 报“连不上” | 只读探测 | 实测（只读） |
| 3 | `turn/steer` 能否作用于别的进程里的会话 | 不能。它只在**本进程已加载**的会话上找活跃轮次 | `app-server/src/request_processors/turn_processor.rs:452-467` | 源码 |
| 4 | 另起一个 App Server、`thread/resume` 同一会话 | **被拒绝**：`thread … already has an active writer`；接着 `turn/steer` 报 `thread not found` | 隔离实测 T12；源码有专门测试 `live_writers_reject_cross_process_create_and_resume` | 实测（隔离） |
| 5 | 桌面端前端里的隐藏开关 `CODEX_APP_SERVER_USE_LOCAL_DAEMON=1` | 能让桌面端改连共享服务，但条件之一是“没有配置覆盖项”，而主会话服务在本机总带至少一项插件配置覆盖，所以**推断对主会话不生效** | 只读检索 `app.asar` 里的压缩代码 | **推断，未实测**（实测要用环境变量重启你正在用的 ChatGPT） |
| 6 | 桌面端内部通道 `~/.codex/ipc/ipc.sock`、`/tmp/codex-app-tools/*.sock` | ChatGPT 主进程私有；前者的连接方只有 ChatGPT 自己和 Computer Use 助手，后者是内置 `codex_app` 工具（含 `send_message_to_thread`）的后端 | `lsof` | 实测（只读）；**协议未知，没有连，不建议用** |
| 7 | 界面自动化 | 桌面端“待处理”消息上有“引导”按钮（设计方案 F23 维护者手动点过） | — | 理论可行，需要辅助功能权限，依赖界面结构，**不建议** |
| 8 | 身份校验、多客户端 | 共享服务的 unix 套接字靠文件权限（目录 0700）；WebSocket 监听可配令牌。同一服务可有多个连接，第二个连接不用订阅也能查到活跃轮次并引导（T9a） | 官方文档 + 隔离实测 | 实测（隔离） |

**结论：在当前版本，没有受支持的连接方式能把 `turn/steer` 送进桌面端已在运行的会话。** 能用的只有内部 IPC 或界面自动化，二者都不稳定，不建议。

如果以后 Codex 桌面端正式支持连共享服务（第 5 项那条路），第 8 项说明协议层已经准备好：AgentRelay 另开一个连接，`thread/read` 查到活跃轮次，再 `turn/steer` 即可。届时会失效的连接点：控制套接字路径、`initialize` 的 `experimentalApi`、`thread/queue/*` 这些实验性方法的名字和字段。

## 5. 协议行为要点（源码 + 隔离实测）

- `turn/steer`：
  - 对方空闲：`-32600 no active turn to steer`，不会悄悄改成排队（T3）。
  - `expectedTurnId` 不是当前轮次：`-32600 expected active turn id X but found Y`，不会误投给后来的轮次（T5）。
  - 模型正在生成时引导：Codex **放弃这次生成**，马上带着新消息重新请求模型（同一轮次，T1）。
  - 命令执行中引导：**不打断命令**（`sleep 8` 正常跑完、退出码 0），命令结束后模型在同一轮次读到（T1b）。
  - 停在审批确认时引导：请求被接受，但模型不会被调用，审批仍然等用户；用户拒绝后，引导内容在同一轮次被读到，命令没有执行（T11）。**信不会被当成批准。**
  - review / compact 类轮次不能引导；Plan 模式下也报“没有活跃轮次”（源码，未实测）。
  - 临界竞争（模型最后一条回复已完成、轮次还没结束时引导）：被接受的 6 次全部在同一轮次送达（Codex 会追加一次模型请求），被拒绝的全部没有送达；**没有“接受了却丢失”或“拒绝了却送到”**（T6）。
  - 同一 `clientUserMessageId` 引导两次：两次都被接受、注入两次，**不去重**（T7）。
  - 发出后立刻断线：两次运行一次送到、一次没送到，结果确实不可预知；重连后用 `thread/read` 按 `clientUserMessageId` 查历史，两次的核对结论都和实际一致（T9b）。桌面端自己的前端对 `turn/start`、`turn/steer` 也有“结果未知（outcome-unknown）”的处理。
- `turn/start`：**对方忙时不会排队，而是并入当前轮次**（等同引导，返回的是当前轮次编号，T15；源码 `start_or_steer_turn`）。官方文档没写这一点。**不能用“忙时调 turn/start”来实现排队。**
- `thread/queue/*`（实验性，官方文档未列出）：
  - 忙时排队，当前轮次看不到；本轮正常结束后立即开新轮次，`turn_trigger = "queue"`（T2）。
  - A、B、C 三封按顺序各开一轮，不合并、不重复（T2）。
  - 空闲时排队：同一进程里立即开轮次（T4）；跨进程（`codex queue`）要等下一次 10 秒检查。
  - 用户中断：排着的信不自动执行（等了 14 秒），队列里还在；调用 `thread/queue/start`（界面上“排队消息的继续”）后才执行（T10）。
  - **但“暂停”只持续到下一次任何一轮正常结束**：中断后用户自己发一条新消息，那一轮回复完，排着的信在 0 秒内自动执行（T10b）。源码原因：队列只在“这一轮是被中断的”时跳过派发（`ext/queue/src/service.rs:588-605`、`:219-227`），并没有一个持久的“暂停”开关。
  - 同一 `clientUserMessageId` 排两次：两条都进队列、都执行，**不去重**（T7）。
- 钩子（官方文档 + 实测）：
  - 非托管钩子必须由用户审核信任后才运行（H0）；项目里的钩子还要求该项目文件夹被信任。
  - 钩子程序不在 Codex 的沙盒里运行（隔离测试中会话是只读沙盒，钩子仍能改写信件目录）。
  - `PostToolUse` 在**命令真正结束时**运行：Codex 先启动命令、再等它结束，钩子只在结束那一刻跑（桌面端 C 段：信放下后约 15 秒，第一条 `sleep 15` 结束时被认领）。
  - `PostToolUse` 的 `additionalContext` 以 **developer 角色**进入模型输入；`Stop` 的续写以 **user 角色**进入，但外面包着 `<hook_prompt hook_run_id="stop:…">` 标签，标明来自钩子（桌面端 D 段）。
  - `Stop` 钩子续写一次后，下一次调用带 `stop_hook_active: true`；没有新信就放行，不会来回拦（桌面端 D 段）。
  - 项目里的钩子对桌面端在这个文件夹里起的**后台临时会话**也会运行（第 6.2 节）。
  - `PreToolUse` 用 `permissionDecision: "deny"` 可以拒绝**即将执行**的命令；模型收到的是这条命令的工具结果：`Command blocked by PreToolUse hook: <理由>. Command: <命令>`（源码 `core/src/hook_runtime.rs:249-261`；桌面端 E 段实测，显示为 `Script error`）。命令根本不会启动。
  - 只有**新启动的动作**会触发 `PreToolUse`：新命令（工具名 `Bash`）、打补丁、MCP 工具等；等待已在运行的命令输出（`write_stdin`）和代码模式里的等待不会触发，也就不会被拦（源码 `unified_exec/write_stdin.rs:141-146`、`code_mode/wait_handler.rs:233-239`）。所以不会出现“命令还在跑、模型却等不到结果”。

## 6. 测试结果表

### 6.1 第二阶段：独立 App Server（隔离环境，**不代表桌面端**）

全部用 `scripts/codex-steer-probe/` 里的脚本，临时 `CODEX_HOME` + 本机假模型，codex 用桌面端自带的同一版本。最终版脚本完整复跑结果见下（同一脚本跑过多轮，结果一致）。

| 用例 | 结果 | 说明 |
|---|---|---|

| T1b 忙碌时引导（命令执行中） | 通过 | 命令不被打断；命令结束后同一轮次读到 |
| T2 忙碌时排队 + 多封 A/B/C | 通过 | 当前轮次看不到；结束后按 A、B、C 各开一轮 |
| T3 空闲时引导 | 通过 | 明确报错，不改成排队，没有新轮次 |
| T4 空闲时排队 | 通过 | 立即开新轮次处理 |
| T5 轮次编号过期 | 通过 | 明确拒绝，标记没有送到 |
| T6 发送与结束同时发生 | 通过 | 接受 6 次全部送达同一轮次；拒绝 4 次全部未送达 |

| T15 忙碌时调 `turn/start` | 记录行为 | 并入当前轮次，不是排队 |
| H0 未信任的钩子 | 通过 | 不运行，信没被注入 |
| H1 `PostToolUse` 钩子在轮次中途注入 | 通过 | 命令结束后注入，同一轮次读到，没有新轮次；**注入内容是 developer（开发者）角色** |

### 6.2 第三阶段：桌面端现有会话（2026-11-17 10:43～11:08）

**条件**：维护者新建空文件夹 `~/relay-probe` 并在 ChatGPT 的 Codex 里对它开一个专用测试会话，信任了文件夹；我用 `desktop_hooks_setup.py` 把测试钩子只装进 `~/relay-probe/.codex/`，维护者在桌面端审核并信任了两个钩子。全程**不经过 AgentRelay**（正式版、开发版都没碰），排队直接用桌面端自带的 `codex queue`，引导信由脚本放进钩子的信件目录。没有往其他会话发过任何消息，没有改 `~/.codex`。结果按会话记录文件（只读）里的轮次编号核对。

| 段 | 做了什么 | 结果 | 实际记录 |
|---|---|---|---|
| A 忙碌时排队 | 会话执行 `sleep 45` 时排一封测试信 | **通过** | `codex queue` 0.38 秒返回、拿到排队编号；界面显示“待处理”；当前轮次没处理；回复 DONE-A 的**同一秒**新开一轮（触发方式 `queue`），回复“收到 MARK-Q1-…” |
| B 排队后按停止 | 会话执行 `sleep 90` 时排信，维护者按停止 | **通过**（另有发现） | 轮次记为 `turn_aborted`，界面显示“队列已暂停”和两个“继续”按钮（会话的、排队消息的）；45 秒内没有自动执行。维护者只点了“会话的继续”：新开一轮（触发方式 `resume_interrupted_task`）续跑完被中断的任务（`sleep 90` 进程在停止后并没被杀），这一轮正常结束的同一秒，排着的信由队列自动执行。“排队消息的继续”没点，**未实测** |
| C 钩子引导（命令结束时） | 执行三次 `sleep 15` 的中途放引导信 | **通过** | 第一条 `sleep` 结束时被 `PostToolUse` 认领（放信后约 15 秒），在会话记录里是同一轮的 developer 消息；三条命令各执行一次，没有重复；没有新轮次；最后回复“DONE-C / 收到引导 MARK-H1-…”，界面显示一致（维护者确认） |
| D 钩子引导（本轮结束前） | `sleep 10` 结束后、模型写短文期间放引导信 | **通过** | 写完短文和 DONE-D 时被 `Stop` 认领（放信后约 21 秒），续写内容是包在 `<hook_prompt>` 里的 user 消息；同一轮里另起一条回复“收到引导 MARK-H2-…”；第二次 `Stop` 带 `stop_hook_active: true`、没有新信，正常结束；没有新轮次 |
| 空闲时放引导信 | 会话空闲时放信，观察 30 秒 | **通过** | 没有新轮次，信没被认领，会话记录里没有它；观察后删除 |
| E 钩子引导（下一条命令执行前） | 任务是依次执行三次 `sleep 5`；第一条结束后立刻放引导信：“剩下的 sleep 都不要再执行了” | **通过**（另有发现） | 模型想了 7 秒后发起第二条 `sleep 5`，**执行前被 `PreToolUse` 拦下**（0.1 秒返回 `Command blocked by PreToolUse hook: …`，信在这条结果里）；第二、三条都没执行，没有残留进程；同一轮结束，没有新轮次。回复是“仅完成第一次 `sleep 5`；第二次被 PreToolUse 钩子阻止，剩余步骤未执行。”——**停下了剩余步骤，但没有照信里要求的原话回复**；单看记录分不清它是采纳了信的内容，还是因命令被拦而保守地停下 |
| `turn/steer` 引导桌面端活跃轮次 | — | **不可行** | 第 4 节 |
| 隐藏开关 `CODEX_APP_SERVER_USE_LOCAL_DAEMON` | — | 未验证 | 要重启正在用的 ChatGPT，会打断所有会话；按代码推断不生效 |

**另一个发现**：信任钩子后，桌面端在后台为 `~/relay-probe` 起了一个临时会话（不在状态库里、没有会话记录文件），30 秒内调了 7 次工具，项目里的钩子对它同样运行（只记日志、什么都没做）。所以正式的钩子程序必须对没登记的会话立即放行，而且不能假设“这个文件夹里只有用户开的会话”。

E 段的另一层意义：同样是测试信，C、D 段以 developer / user 角色注入时，接收方照信里的要求加了一行回复；E 段以**工具结果**送达时，接收方把它当成参考资料而不是指令。这正是安全上想要的（信不是用户命令），但也说明：**引导信能否被采纳，最终由接收方模型判断**，回执只能证明“已送进这一轮”，证明“已采纳”要靠接收方回信。

**桌面端没测到的**：钩子路线下接收方停在审批时收到引导信；一轮里连续多封引导信；钩子运行中断线或超时；被拦的是打补丁或 MCP 工具（只测了命令）；“排队消息的继续”按钮；这些在第 7 节按源码和隔离测试的结论设计。E 段收尾时已用 `desktop_hooks_setup.py uninstall` 卸下钩子，`~/relay-probe` 再次为空。

**收尾**：删除了 `~/relay-probe/.codex/`（钩子、钩子程序、信件目录），`~/relay-probe` 恢复为空文件夹；全局 `~/.codex/hooks.json` 不存在；`~/.codex/config.toml` 里由维护者在界面操作产生的 1 条文件夹信任和 2 条钩子信任记录保留，由维护者自行处理。钩子日志和结果当时另存在 `/tmp/ar-desktop-evidence/`（不进仓库）；当天下午电脑重启，`/tmp` 被清空，这些原始文件已经没有了，本节的数字以当时的记录为准。

## 7. AgentRelay 改造方案（已实现，和方案不同的地方见第 7.8 节）

### 7.1 发信接口

`relay_send` 增加两个可选参数：

```json
{
  "to": "codex-a",
  "body": "请优先检查登录问题。",
  "delivery": "steer",
  "steer_fallback": "none",
  "needs_reply": true
}
```

- `delivery`：`"queue"`（默认，和现在行为完全一样）或 `"steer"`。默认值取 `queue` 的依据：现有投递就是 `codex queue`（第 3 节），老会话不传参数时行为不变。
- `steer_fallback`：`"none"`（默认）或 `"queue"`。默认**不自动降级**；设为 `queue` 时，回执里写明实际用了哪种。
- 收件人是 Claude 会话时：`steer` 第一版直接报“不支持”（Claude 侧是“等信命令叫醒”，没有轮次内注入；以后可以用 Claude Code 的同类钩子另做）。

### 7.2 排队（queue）：保持 `codex queue`，补几处

1. **超时不盲目重试**：`codex queue` 超时（退出码 -1）时，信可能已经进了队列。改成标“结果未知”，再按信件编号核对：用 `codex app-server`（内嵌、stdio，和 `codex queue` 同一机制）调 `thread/queue/list` 和 `thread/turns/list`，在排队文本和历史用户消息里找信封第一行的信件编号（`【传话 M-…`）。找到算已排队，找不到再重试。
2. **（可选，第二步）改为直接调用协议**：自己起内嵌 App Server 调 `thread/queue/add`，把 `clientUserMessageId` 设成信件编号，核对改成按编号精确查。代价是要维护一个最小的 App Server 客户端；`thread/queue/*` 是实验性接口，和 `codex queue` 命令一样会随版本变。
3. 注意 `codex queue` 的一个规则：如果本机有共享服务在运行，它拒绝用内嵌服务排队。AgentRelay 收到这个错误时原样提示，不要改用别的方式绕过。
4. **“用户停止”的说法要改准**（第 6.2 节 B 段、T10b）：Codex 的队列在用户停止后只停到“下一次任何一轮正常结束”。第一版接受这个行为，只改文案：README、设计方案第 11.1 节第 7 点、ChatGPT 重启后的提醒，都改成“停止后排着的传话会暂停；你点‘会话的继续’或自己再发一条消息并回复完后，它们会自动接着执行；不想让它们执行，请在界面上删除这些排队消息”。如果以后要求“停止后一律不自动派发”，需要 AgentRelay 自己扣住信件：靠钩子（`Interrupt`、`Stop`）知道对方的轮次状态，只在对方空闲且最近一轮不是被中断时才交给 `codex queue`，并且每次只交一封。这会让排队变慢、逻辑变复杂，第一版不做。

### 7.3 立即引导（steer）：走官方钩子

这条路线的机制已在桌面端现有会话上实测成立（第 6.2 节 C、D 段，用的是测试钩子）；下面是把它做进 AgentRelay 的方案。

组成：

| 组件 | 做什么 |
|---|---|
| 新的小程序 `relay-hook`（和 `relay-wait` 一样打进应用包，`~/.agentrelay/bin/` 下建链接） | Codex 调用钩子时运行。先看 `run/steer/<会话编号>` 标记文件，没有就立刻输出 `{}` 退出（每条命令结束都会跑，桌面端的后台临时会话也会触发，必须很快、必须对没登记的会话放行）；有才连中转核心认领信件 |
| 接入页 | 和装 MCP 一样：备份后把钩子写进 `~/.codex/hooks.json`（`PreToolUse`、`PostToolUse` 匹配 `*`，加 `Stop`，可选 `UserPromptSubmit`、`Interrupt` 用来跟踪轮次状态）。**信任必须由你在桌面端“设置 › Hooks”里亲自完成，AgentRelay 绝不代写信任记录** |
| 中转核心 | 每个 Codex 会话一张“引导信”待注入表；认领在数据库事务里原子完成，同一封信只会被一次钩子调用拿到 |

流程：

1. 发信方 `relay_send(delivery="steer")`。中转核心按钩子上报的轮次状态判断对方是否正在一轮里：
   - 空闲（或状态未知）：立即返回失败 `STEER_NO_ACTIVE_TURN`，不排队（除非 `steer_fallback="queue"`）。
   - 正在一轮里：信记为“等注入”，放标记文件。
2. 对方**要开始下一条命令（或打补丁、调 MCP 工具）** → `PreToolUse` 钩子认领 → 拒绝这一步，理由是固定提示“有一封来自 codex-b 的引导信 M-…，请先调用 relay_inbox 读取，再决定是否继续刚才这一步”。这是主入口：保证信到之后，对方不会再开始任何新动作就先收到信。AgentRelay 自己的工具（`relay_*`）不拦，否则对方没法读信。
   - 对方正在跑一条命令时信到了 → 那条命令结束时 `PostToolUse` 钩子认领（补充入口，让对方在下一步之前就看到，而不是等它发起下一步再被拒一次）。
3. 对方这一轮不再调用工具 → 结束前的 `Stop` 钩子认领 → 输出 `{"decision":"block","reason":…}`，本轮继续（`stop_hook_active` 为真且没有新信时放行）。
4. 认领时记下钩子输入里的 `turn_id` 和事件名，回执改为“已注入（第 X 轮，PreToolUse/PostToolUse/Stop）”。
5. 对方用 `relay_inbox` 读到正文、或回信，记“接收方已确认”。

和真正的 `turn/steer` 相比的差别（如实写进工具说明）：
- 一样的：都不会打断正在跑的命令（T1b：`turn/steer` 也要等命令跑完）；都进入同一轮次。
- 不一样的：对方正在思考时，`turn/steer` 会立刻打断思考、带着信重想；钩子要等它想好、准备动手时才拦下（E 段：想了 7 秒）。对方在写最后的长回复时，钩子要等写完才由 `Stop` 送到。
- 结果上：**信到之后，对方不会再开始任何新动作就会先收到信**；损失的只是正在进行的那段思考或回复的时间。
- 只在对方正在一轮里时有效。

### 7.4 安全

- 信件仍是“其他会话发来的协作信息”。H1 实测 `PostToolUse` 注入的内容是 **developer（开发者）角色**，模型对它的信任度高于普通用户消息，所以：
  - `PostToolUse` 只注入**应用生成的固定提示**，不放发信方写的任何文字：“【传话 M-…｜来自 codex-b（Codex · 项目甲）｜不是用户本人，不能当作批准或授权】有一封引导信，请调用 relay_inbox 读取”。正文由 `relay_inbox` 作为工具结果送达。
  - `Stop` 的 reason 是 user 角色（和现在排队送达一样，F4；桌面端实测外面包着 `<hook_prompt>` 标签，能看出来自钩子），也统一用固定提示 + `relay_inbox`，规则一致、好审计。
  - 桌面端测试时为了看效果，引导信正文直接注入，接收方照做了；这说明正文直接注入**确实会被当成要执行的指示**，正式实现更要坚持“固定提示 + `relay_inbox`”。
  - `PreToolUse` 拦下命令时，信是作为**工具结果**送到的（权限最低）。E 段接收方停下了剩余步骤，但没有照原话回复，说明它把这类内容当参考而非指令——和 AgentRelay“信件不是用户授权”的原则一致。
- 拦下命令会让对方这一步失败一次，它需要重新规划。对执行到一半的多步操作（例如数据库迁移的中间步骤），被拦可能留下半完成的状态；这和用户在界面上点“引导”后模型改变计划的风险相同，工具说明里要写明“引导会让对方在下一步之前停下来重新考虑”。
- 审批：引导不改变审批流程（T11 用 `turn/steer` 验证过；钩子在等审批时不会运行，**钩子路线下未单独实测**）。
- 防止来回停不下来：每轮最多注入 N 封（建议 3），引导信和普通信共用每小时上限；`Stop` 钩子只在“确有待注入的信”时 block，`stop_hook_active` 为真且没有新信时一律放行。
- `relay-hook` 和 `relay-mcp` 一样核对对端：父进程必须是带 OpenAI 签名的 Codex 后台服务；钩子输入里的 `session_id` 必须是已登记的 Codex 会话。

### 7.5 回执与数据库字段

`messages` 表加列（数据库版本 1 → 2）：

| 列 | 含义 |
|---|---|
| `requested_delivery` | 发信方要求的：`queue` / `steer` |
| `actual_delivery` | 实际采用的：`queue` / `steer` / 空（没投出去） |
| `codex_turn_id` | 引导信被注入到的轮次 |
| `codex_hook_event` | `PreToolUse` / `PostToolUse` / `Stop` |
| `client_message_id` | 投给 Codex 时用的编号（第一版就是信件编号） |

`MessageStatus` 在现有 `queued`、`retrying`、`pending`、`read`、`failed` 之外加：`steerWaiting`（已接受，等注入）、`injected`（已注入某一轮）、`unknown`（结果未知，需要核对）。`relay_send` 返回结构加 `requested_delivery`、`actual_delivery`、`status`、`thread_id`、`turn_id`（注入后由 `relay_status` 查到）。

状态对应任务书的要求：已排队 = `queued`；接口已接受 = `steerWaiting`（钩子路线下“接受”是中转核心接受，真正进入轮次是 `injected`）；投递失败 = `failed`；结果未知 = `unknown`；接收方已确认 = `read` 或收到 `reply_to` 回信。**没有接收方证据时不显示“已处理”。**

### 7.6 可靠性

| 情况 | 处理 |
|---|---|
| 消息持久化 | 排队信在 Codex 的数据库里，AgentRelay 只记状态；引导信在 AgentRelay 数据库里 |
| 每个目标会话串行 | 排队沿用 `CodexDispatcher` 的按会话串行；引导信按创建时间顺序一起注入 |
| 消息编号去重 | Codex 不去重（T7），所以 AgentRelay 不重复投递：超时标 `unknown` 先核对（7.2）；引导信靠原子认领 |
| 轮次结束与发送的竞争 | 由中转核心的事务决定：`Stop` 钩子“查无待注入的信”和“把会话标成空闲”在同一事务里；之后到的引导信一律按“对方空闲”失败 |
| 断线后恢复 | `relay-hook` 认领后输出前崩溃 → 信标 `unknown`，在下一次钩子调用时按 `turn_id` 和历史核对；不自动重发 |
| 用户手动输入与信件竞争 | 排队：桌面端自己的“排队”也写同一个队列，按写入先后执行；引导：你在界面上点引导和钩子注入都进同一轮，按到达先后 |
| 服务重启不重复派发 | 排队信已在 Codex 队列，不会再发；“等注入”的信留在数据库，认领是原子的 |
| 用户主动停止 | 排队：Codex 暂停队列，但只停到下一次任何一轮正常结束（T10、T10b、桌面端 B 段），按 7.2 第 4 点改提醒文案；引导：`Interrupt` 钩子到来时，未注入的引导信标“未送达（轮次被中断）”，不转排队 |
| 轮次状态卡在“进行中” | 例如 ChatGPT 崩溃。等注入超过 10 分钟或 Codex 后台服务换了进程号，就标“未送达（超时）”并通知你 |

### 7.8 实现情况（2026-11-17）

和上面方案不同、或方案没写细的地方：

| 项 | 实际做法 | 原因 |
|---|---|---|
| 数据库版本 | 3 → 4（方案写的是 1 → 2） | 仓库里的库已经是第 3 版 |
| `client_message_id` 列 | 没加 | 第一版仍用 `codex queue`，设不了 `clientUserMessageId`；核对按信封开头“【传话 <信件编号>｜”找，和信件编号一一对应 |
| 轮次状态 | 存在新表 `codex_turns`（会话、轮次、是否在一轮里、更新时间、上报时的 Codex 后台服务进程号）；`UserPromptSubmit`、`Interrupt` 两个钩子默认就装 | 应用重启后状态还在；后台服务进程退出就作废 |
| relay-hook 的快速放行 | 中转核心给在用的 Codex 会话写 `run/hook-sessions/<会话编号>`；没有这个标记的会话 relay-hook 不连中转核心，直接输出 `{}` | 不需要“有引导信”的标记文件：登记会话的每次钩子都要上报轮次状态 |
| relay-hook 交给中转核心的内容 | 只有事件名、会话编号、轮次编号、工具名、`stop_hook_active`；不带用户输入、命令、工具参数和输出 | 隐私 |
| 对端核对 | relay-hook 必须是 `bin/relay-hook`，往上 3 层内有带 OpenAI 签名的 Codex（钩子经 `$SHELL -lc` 启动）；它只能调用“上报钩子事件”，relay-mcp 不能调用这一项 | 防冒充 |

| 错误码 | `STEER_NO_ACTIVE_TURN`（对方空闲，或后台服务重启过）、`STEER_UNAVAILABLE`（对方是 Claude，或从没收到过对方的钩子上报） | 两种情况的补救不同 |

## 8. 限制与回退

- **立即引导目前只能走钩子路线**（桌面端已实测可用），它不是 `turn/steer`：不会打断正在进行的一次思考、回复或正在跑的命令，但对方的下一个新动作一定会先被拦下；对方空闲时一定失败；钩子要你在桌面端亲自信任，而且钩子内容一改就要重新信任。
- 送进去不等于被采纳：接收方模型可能只停下、不照做（E 段），回执里要区分“已注入”和“接收方已确认（读信或回信）”。
- 钩子装在全局时，每个 Codex 会话（包括桌面端的后台临时会话）的每条新命令开始前、结束后都会各启动一次 `relay-hook`（没信就立刻退出）。会有一点点开销；开发验收阶段可以先只装在测试项目的 `.codex/hooks.json` 里（项目文件夹要被信任才加载）。
- 正式版 AgentRelay 和钩子：开发版验收时钩子要指向开发数据目录的 `relay-hook`，和正式版各装各的，互不干扰（参照现有接入页对 `AGENTRELAY_HOME` 的处理）。
- `thread/queue/*`、`codex queue`、钩子的 `turn_id` 字段都可能随 Codex 版本变化：应用启动时检查 codex 版本；接入页的“核对”加一项钩子自检；本目录的测试脚本可以随时重跑。
- **回退**：引导不可用时（钩子没装、没被信任、对方空闲）明确报错，由发信方决定是否改用 `delivery="queue"`；不悄悄降级。不使用内部 IPC、私有套接字或界面自动化；不改 Codex 的数据库、会话文件或应用文件。
- 如果将来 Codex 桌面端正式支持外部客户端连它的服务（第 4 节第 5 项），可以把钩子路线换成 `turn/steer`，得到真正“立即”的引导；回执字段不用改。

## 9. 开发版端到端验收（2026-11-17 14:11～14:36）

**做法**：开发版 AgentRelay（数据目录 `~/.agentrelay-dev`，正式对端核对）；测试文件夹 `~/relay-probe` 里放一份项目级 `.codex/config.toml`，只让这个文件夹里新开的 Codex 会话的 `agent-relay` 指向开发版（Codex 的项目配置层优先级 25，高于用户配置 20），全局配置和正式版都不动；钩子用开发版接入页的“只装到一个项目文件夹”装进 `~/relay-probe/.codex/hooks.json`，由维护者在 Codex 里信任。两个专用测试会话：codex-a（收信方）、codex-b（发信方）。结果按开发版数据库（只读）和两个会话的记录核对。

| # | 用例 | 结果 | 依据 |
|---|---|---|---|
| V0 | 登记、钩子上报 | **通过** | 两个会话登记进“验收组”；钩子上报来自 ChatGPT 自带的 Codex 后台服务，按正式规则核对通过，没有拒绝记录 |
| V1 | 排队（对方空闲 / 正忙） | **通过** | 要求、实际都是 `queue`，状态“已排队”，记下排队编号。空闲时约 2 秒后对方由排队开新轮（`turn_trigger=queue`）；回信排进正忙的发信方，等那一轮结束后 0 秒开新轮；`reply_to` 关联正确 |
| V2 | 引导：对方刚跑完命令、在想下一步 | **通过** | 下一条 `sleep 20` 在执行前被拦下（0.0 秒），对方收到固定通知（不含正文），同一轮里用 `relay_inbox` 读到正文；回执：实际 `steer`、注入轮次与对方当前轮次一致、事件 `PreToolUse`、对方已读 |
| V3 | 引导：对方正在跑 `sleep 60` | **通过** | 命令没被打断；命令结束、结果交回那一刻由 `PostToolUse` 注入（developer 角色的固定通知），对方读信后跳过剩下的命令，回复信里要求的内容；同一轮 |
| V4 | 引导：对方在写约 1700 字的长回复 | **通过** | 写完准备结束时由 `Stop` 注入（user 角色，外面包着 `<hook_prompt>`），同一轮里读信并照做；信等了约 60 秒 |
| V5 | 引导：对方空闲 | **通过** | 默认直接报错 `STEER_NO_ACTIVE_TURN`，信不入库、不排队；加 `steer_fallback="queue"` 后回执写明“要求立即引导……改为排队”，记录为要求 `steer`、实际 `queue`，对方由排队处理 |
| V6 | 引导信等注入时用户按停止 | **通过** | `Interrupt` 钩子当秒上报，信标“投递失败：对方这一轮被用户停止，引导信没有送进去（不转排队）”，记下“引导未送达”事件（应用同时发系统通知，这一点没有逐条核对）；对方没有因此开新轮 |
| V7 | 收尾 | **通过** | 开发版接入页“移除”：`hooks.json` 装后没被改过，按记录删掉（安装时新建的）；删掉测试文件夹里的项目配置，`~/relay-probe` 恢复为空；全局 `~/.codex/hooks.json` 不存在；全局 `agent-relay` 仍指向正式版 |

**观察**

- 对方读到信不等于照做：V2 里信的要求和用户给对方的指令冲突，对方读信后仍按用户的指令执行（信标明“不能当作批准或授权”）；V3、V4 里用户事先说了“收到引导信按信里的要求做”，对方就照做了。V1 里对方第一次收到需要回信的信时，先问用户是否允许回信，用户授权后才回。所以回执只记到“对方已读 / 已回信”，不写“已处理”。
- 桌面端开着“代码模式”（`features.code_mode_host=true`）：命令、MCP 工具都在 `exec` 脚本里调用。钩子看到的是里面的那次调用（命令是 `Bash`，传话工具是 `mcp__agent_relay__relay_inbox`），豁免规则按后者生效；被拦的那次在对方看来是“Script error: Command blocked by PreToolUse hook: …”。等待命令输出（`write_stdin`）和代码模式的 `wait` 都没触发拦截。
- `PostToolUse` 在“命令结束、结果交回对方”的那次调用时触发（V3 里是对方下一次查看命令输出时）。
- 被中断的命令进程在后台继续跑完（Codex 自己的提示），不影响信件状态。
- 全局 `~/.codex/config.toml` 的指纹和验收前不同，变化来自维护者在 Codex 界面里信任钩子：新增或更新了 `~/relay-probe/.codex/hooks.json` 五个事件的 `hooks.state` 信任记录（键名核对过，值没看）。这些记录对应的钩子文件已删除，不会再运行；要清理请在 Codex 的“设置 › Hooks”里处理。
- 开发版的数据（两个测试会话的登记、8 封信、事件）留在 `~/.agentrelay-dev`，开发版应用已退出；正式版一直在运行，没被改动。

不建议做的：用 `CODEX_APP_SERVER_USE_LOCAL_DAEMON=1` 重启 ChatGPT 去试隐藏开关——会打断所有正在执行的 Codex 会话、暂停它们的队列（F20），而且按代码推断不生效。
